## 1. Current State Summary

The memory-and-learning domain spans 267+ files / ~100K LOC across AgentDB, ReasoningBank, HNSW vector search, embeddings, pattern storage, RL, consciousness subsystems, and the V3 claude-flow memory and intelligence layers. Quality varies dramatically — from 98% (neural-network-implementation data/mod.rs pre-audit) to 0% (self-modification-engine.ts pure fabrication, agentdb-adapter.ts misnamed zero-AgentDB store, memory-bridge.ts dead at runtime). Sessions R136-R141 complete the Middle Layer analysis: R136 mapped the V3 memory layer, R140 deep-read the intelligence and SONA optimizer files, and R141 ran Rust compilation audits across all relevant workspaces, producing ground-truth compilation evidence.

**V3 Memory Architecture (R136)**: The intended V3 architecture (ADR-053) envisions memory-bridge.ts as a comprehensive 28-function TS-to-AgentDB bridge with hybrid scoring (0.7 semantic + 0.3 BM25 RRF), MutationGuard, ExplainableRecall. This file scores 82-85% on code quality BUT is NOT compiled into the npm dist (0% runtime reachability). The ACTUAL runtime path is: index.ts UnifiedMemoryService (pure 14-method delegation layer) → AgentDBAdapter (MISNAMED — zero AgentDB connection, plain Map<string, MemoryEntry> in-memory store) → hnsw-index.ts (PURE JAVASCRIPT HNSW from scratch). No native ruvector, no hnswlib-node, no WASM. The JS HNSW has a CRITICAL level distribution bug: getRandomLevel() uses coin-flip p=0.5 instead of standard HNSW p=1/M (~0.0625), producing far too many high-level nodes and degrading search from O(log n) toward O(n). Additionally, hnsw-index.ts has ZERO persistence — all vectors are lost on restart.

**THREE parallel embedding pipelines exist in V3 memory** — (a) memory-initializer.ts has its OWN 3-tier pipeline (@xenova/transformers → agentic-flow → hash) that never references EmbeddingService, making it the 14th+ parallel subsystem; (b) auto-memory-bridge's LearningBridge uses sin(hash) 768-dim hash-based embeddings; (c) the project-wide EmbeddingService is never connected to V3 memory at all. Dimension mismatch is systemic: memory-initializer metadata says 768, xenova returns 384, hash returns 128.

**R20 root cause is structurally replicated in V3**: AgentDBAdapter's embeddingGenerator field is optional and defaults to undefined, with 2 of 4 factory functions omitting it entirely. The pattern that broke AgentDB semantic search in V1 (EmbeddingService never initialized) is architecturally reproduced in V3's primary memory adapter.
